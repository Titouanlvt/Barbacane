# Barbacane v2.3.0 — journal structuré, export Syslog, conservation

Sécurité d'abord : écarts bloquants n° 1 (purge non implémentée) et n° 3 (pas d'export du journal
hors serveur) de l'étude E1, décision de l'utilisateur du 22/11 (conservation configurable).
Serveur seulement ; la borne ne change pas (numéro de version). Publiée le 23/11/2026.
Références : [`journal-structure.md`](../suite/journal-structure.md),
[`journal-syslog.md`](../suite/journal-syslog.md), [`journal-conservation.md`](../suite/journal-conservation.md).

## Journal structuré

- Une ligne JSON par événement d'audit et de passage : `schema`, `serveur`, `id` (unique et stable),
  `n`, `horodatage` RFC 3339 UTC, `gravite`/`gravite_code` RFC 5424, `categorie`, `type`, `acteur`,
  `donnees`, `empreinte`/`prec` (la chaîne reste vérifiable chez le collecteur).
- Aucun nom de fichier (D2), pseudonymes seulement pour les utilisateurs des bornes.
- Export de tout le journal conservé dans la Console (administrateur, auditeur ; journalisé) et
  `barbacane-audit structurer`.

## Export Syslog (RFC 5424)

- **TLS 1.3** (RFC 5425, rustls, suites et groupes D6) : certificat du collecteur vérifié contre l'AC
  configurée et le nom attendu ; **mTLS** facultatif avec une clé tirée par le serveur (demande de
  certificat affichée, la clé ne quitte jamais le serveur). Ou **en clair** (TCP RFC 6587, UDP
  RFC 5426) : non recommandé, avertissement permanent, audité.
- Réglage dans la Console (administrateur), **double validation** pour toute modification et pour la
  désactivation ; le pare-feu n'ouvre que la cible validée (réseau d'administration, compte
  barbacane-svc) : aucune sortie Internet.
- **File persistante** = le journal lui-même + curseur ; **remise confirmée** par fermeture ordonnée
  (TCP, TLS) ; reprise sans perte après coupure, renvois marqués `reprise="1"` (même `id`) ;
  alertes : collecteur injoignable, débordement (100 000 événements), perte (purge avant remise),
  export en clair, exportateur arrêté (Console et tableau de bord).

## Conservation et purge

- Durée réglée dans la Console par **double validation** : défaut 365 jours, de 180 à 730 jours,
  préavis de 7 jours pour toute réduction ; même durée pour les rapports de passage, le journal
  d'audit (journal des administrateurs compris), les correspondances identifiant ↔ pseudonyme et
  les sauvegardes.
- Tâche `barbacane-conservation` (chaque nuit et au démarrage) : purge des rapports de passage,
  **rotation du journal d'audit en segments quotidiens scellés** (ancre signée en tête de chaque
  segment), purge des segments hors durée avec chaîne restante vérifiable, **scellement quotidien**
  automatique. Chaque purge est inscrite au journal avant la suppression.
- `barbacane-sauvegarde` purge les sauvegardes du support monté au-delà de la durée (`purger`).
- Consultations de données personnelles journalisées avec leur cible (rapport de passage consulté,
  fiche utilisateur par pseudonyme, export du journal).

## Migration depuis la 2.2.0

Données conservées ; au premier démarrage, 365 jours **avec préavis de 7 jours** : aucune purge
pendant 7 jours, même pour des données de plus d'un an, puis purge tracée. Le journal 2.2.0
(schéma 1) est relu et rangé en segment. Schéma du journal chaîné : version 2 ; retour arrière vers
la 2.2.0 non pris en charge (la 2.2.0 signale le journal, jamais de lecture silencieuse).

## Revue de sécurité du diff (Claude, 23/11)

Relecture de `git diff 1686843..v230 -- serveur tests` :

| Point examiné | Constat | Suite |
|---|---|---|
| Purge qui effacerait des preuves | purge sur une chaîne altérée, segment du milieu, journal actif | purge seulement des plus anciens, chaîne entière vérifiée d'abord ; trace avant suppression ; tests |
| Ancre de segment forgée | un attaquant sans la clé d'audit supprime le début et réécrit la tête | ancre signée ECDSA P-384, contexte distinct ; test « autre clé » refusé |
| Rotation interrompue | journal actif recréé vide (chaîne repartant de 1) | `.nouveau` repris, sinon refus ; test |
| Outil root dans un dossier de barbacane-svc | liens symboliques, fichiers créés par root illisibles des services | bac à sable systemd (écriture limitée au registre, sans réseau), propriétaire du dossier donné aux fichiers créés |
| Ligne du pare-feu écrite par la Console, lue par root | injection dans nftables, cible hors réseau local | lecture stricte (motif fixe, 64 octets, pas de lien), adresse du réseau d'administration exigée |
| Interblocage pare-feu ↔ exportateur | relance synchrone depuis le service du pare-feu, exportateur ordonné après lui : exportateur arrêté (banc QEMU) | `--no-block`, plus d'ordre `After`, délai de 60 s ; banc rejoué |
| Validation de l'export | le validateur doit valider exactement ce qu'il voit | AC et certificat client désignés par leur SHA-256 dans la demande, revérifiés à l'exécution et à chaque passe |
| Collecteur usurpé | nom ou AC non vérifiés | vérification WebPKI de rustls, nom attendu obligatoire en TLS ; test « mauvais nom » refusé |
| Écritures permanentes | état et curseur écrits (fsync) chaque seconde | écrits seulement s'ils changent, signe de vie chaque minute |
| Données personnelles dans l'export | noms de fichier, identifiants | schéma strict (D2), pseudonymes ; échappement HTML des alertes (test) |

Limites gardées : un code exécuté sous barbacane-svc (conteneur compromis) peut réécrire le réglage
de conservation ou de Syslog dans les bornes revérifiées par root ; clé client mTLS en fichier (TPM :
2.4) ; collecteur séparé à la charge de l'organisme (2.8) ; supports de sauvegarde au coffre purgés
à leur montage.
